1) PURCHASE EDIT / DELETE
==============================================================================
Every purchase line gets Edit + Delete, in two places:
  - /panel/suppliers -> View a supplier -> Purchases table
  - /panel/purchases -> Recent purchases (each line)
Edit corrects item/qty/unit cost/amount/currency/cash-credit; Delete VOIDS (soft, kept in
audit trail, dropped from Owed + totals). Owner/manager only, period-lock guarded, audited.
Endpoints: POST /papi/order-costs/{id}/update (new), POST /papi/order-costs/{id}/delete (void).

==============================================================================
2) CASHBOOK EDIT 500 FIX  (+ CB-0067 correction)
==============================================================================
Bug: TradeCashbookController::update() used $cur without defining it, so every cashbook edit
tried to save currency = NULL -> NOT NULL column rejected it -> 500. Fixed by reading the
currency from the request and falling back to the entry's existing currency.

To move CB-0067 (a conversion = 2 legs) to Jayesh Bhai in one go:
    php artisan tinker
    >>> require base_path('fix-cashbook-holder.php');
  Prints BEFORE/AFTER, audit-logs, runs in a transaction. Set $DRY_RUN=true to preview.
  (Or, after deploy, edit each leg in the panel by hand.)

4) MOBILE "IN TRANSIT"  +  SHIPMENT TRACKER LAST-MILE BRIDGE
==============================================================================
MOBILE (/panel/m): the mobile order flow now includes "In transit"
  (New -> Confirmed -> Preparing -> In transit -> Out for delivery -> Delivered).
  The advance button reads "Mark in transit" then "Send out for delivery"; the In-transit

SHIPMENT TRACKER: the app already ships a full shipment platform (Logistics nav) that tracks
the Kampala->Juba transport leg per shipment (Packed -> Sent to transporter -> Transport
confirmed -> Bus departed/In transit -> Arrived), with a custody ledger, transporter/agent
tokenized pages, a logistics dashboard, and printable box QR labels + manifest. The ONE
missing piece was the service that hands an ARRIVED shipment to the last-mile Delivery — the
"Hand off to delivery" button and the auto-handoff-on-arrival toggle both call
App\Services\Logistics\LastMileBridge, which did not exist (so the button returned an error).

  Added app/Services/Logistics/LastMileBridge.php:
    - On an ARRIVED shipment, creates (or links) an "Awaiting rider" Delivery for the order,
      so it appears on the Delivery Board ready to assign a rider.
    - Idempotent: never makes a second delivery, never disturbs one that already has a rider.
    - deliveries.status is free text (string 16), so the "awaiting" bucket is safe.

  How a seller uses the shipment tracker (after deploy + migrate):
    a. Open a confirmed/paid order -> "🚚 Create shipment" -> enter transporter, origin
       (Kampala), destination (Juba), box count -> shipment created (Packed).
    b. Advance on the shipment page: Dispatch -> Confirm receipt -> Bus departed ->
       Mark arrived. (Or the transporter/agent act via their shared /t/{token} and /a/{token}
       links.) Box-count mismatches auto-flag on the exact leg.
    c. On arrival, "Hand off to delivery" (or auto-handoff) creates the Awaiting-rider task;
       assign a rider -> Out for delivery -> Delivered.

VERIFY (feature 4)
  - Mobile: an active order's Advance button shows "Mark in transit", then "Send out for delivery".
  - Shipment: create a shipment on an order, advance it to Arrived, click "Hand off to delivery"
    -> the order shows on the Delivery Board as "Awaiting rider" (no more error).
