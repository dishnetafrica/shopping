TICKET 3B — PaymentService dual-writes through money.receive (preserving current behaviour)
==========================================================================================

WHAT THIS IS
  The money-in EVENT now flows through the one money.receive capability (Ticket 3A), instead of the
  ad-hoc Emit call. The authoritative OrderCost + CustomerPayment writes and every sync are UNCHANGED.
  This is dual-write: table stays the source of truth (existing ADR-001); the capability owns the event.
  Builds ON 3A — apply 3A first (or together).

APPROVED DECISION — R3 is OBSERVE-ONLY in 3B (Option A)
  The capability emits for EVERY payment (exact parity, zero behaviour change). If a settlement would
  violate R3 (amount > balance), it is LOGGED as evidence but never blocks the payment or the event.
  Fatal R3 arrives only when the capability becomes the front door in Ticket 3C.

HOW PARITY IS GUARANTEED (behaviour is byte-for-byte the same)
  • Same event name ('PaymentReceived'); payload is a superset of the old one (additive, safe).
  • Same CUSTOMER subject: PaymentService resolves phone → CustomerProfile id and passes it, so the
    Customer-360 timeline is unchanged. (This needed a 1-line additive tweak to MoneyReceived::fromInput
    to honour an explicit subject — ReceiveMoney.php is UNCHANGED from your 3A review; 3A tests still pass.)
  • Guarded: the emit can never throw into the payment path (ADR-012). If the capability doesn't emit
    for any reason (R3 observed / error / schema), a fallback mirrors the exact prior emit — so no fact
    is ever lost, and there is never a double-emit (fallback only fires when the capability didn't).
  • Idempotent: the event carries the payment's idempotency_key (or its receipt_no), and record()
    already short-circuits duplicate payments before emitting.
