2 · Architecture Decision Records — one page per major decision

A living log. Two years from now, "why did we build it this way?" has a written answer. Template: Decision · Context · Alternatives considered · Evidence · Tradeoffs · Rejected options · Status. Status stays PROPOSED until evidence moves it to ACCEPTED.

ADR-001 — Money is event-sourcedSTATUS: PROPOSED
Context: money-in has multiple write paths today and the due diligence found a double-record. Money's history, audit, and reversibility are the value.
Alternatives: (a) relational + audit table; (b) CQRS-lite — authoritative table + event log for audit only; (c) full event-sourced money (chosen).
Why (c): one guarded write path, append-only correction, exact rebuild, and a single source every projection and ERP export derives from.
Tradeoffs: read-lag, replay time grows with history, higher cognitive load — accepted only for L1 objects, never L2.
Evidence: PENDING — to be filled by the Week 3–5 replay-correctness, recovery-drill, and audit-reconstruction tests, plus the §4 latency measurements. Until then this decision is a hypothesis (see H3), not law.

First ADRs to open as implementation begins: ADR-002 Trade as one object (tied to H2) · ADR-003 Hybrid kernel L1/L2/L3 boundary · ADR-004 Single AI planner & autonomy limits (H4) · ADR-005 Projection sync vs async (H5).

3 · The six-question feature gate — answered before any code

  1. Which business effect?
  2. Which capability owns it? (exactly one — Rule of One)
  3. Which events are emitted?
  4. Which projections change?
  5. Which invariant is enforced?
  6. How do we test replay?

If all six can't be answered, the feature isn't ready to build — it goes back to design, not into the sprint.

4 · Performance targets — non-functional requirements set before we build

Event sourcing changes operational characteristics; these targets are how we keep that a benefit, not a regression. A capability that can't meet its target is not done.

5 · The project board — the only tracker from here

Freeze the design set. Track the work in four columns. Nothing else.

WEEK
the one goal for the week (from the Blueprint's 16)
EVIDENCE
the metric captured — replay result, latency, % from chat, invariant pass
DECISION
what the evidence changed — a new/updated ADR, or "assumption held"
IMPLEMENTED
the working, shipped, user-visible feature
Definition of a done week: a working feature shipped · measurable evidence captured · at least one invariant test passing · an ADR updated if an assumption changed · and — per the covenant — the product more usable than the week before. If any is missing, the week isn't done.
Operating mode: the Due Diligence, Vision, Architecture, Constitution, Blueprint and Principles are frozen. This system is the living layer on top. Every conversation from here is "we are implementing Week X — here is the evidence." Architecture matures by surviving implementation, not by accumulating documents.
