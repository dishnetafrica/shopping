PAYMENT 500 — REAL FIX (one line): $idem not captured in the transaction closure
=================================================================================

THE REAL ERROR (from your log — thank you)
  unhandled @ PaymentService.php:67
  ErrorException: "Undefined variable $idem"   (POST papi/payments)

ROOT CAUSE
  In App\Services\Money\PaymentService::record, the idempotency key is computed on line 44:
      $idem = ! empty($d['idempotency_key']) ? (string) $d['idempotency_key'] : null;
  and then USED inside the DB transaction closure on line 67:
      'idempotency_key' => $idem,
  …but the closure's use(...) list did NOT include $idem:
      DB::transaction(function () use ($t, $d, $orderNo, $costNote, $customer) {   // <-- $idem missing
  So inside the closure $idem was undefined → ErrorException → 500 → the papi handler's generic
  "Something went wrong on our side." This hit EVERY payment path that goes through the one recorder
  (Collect Run, Customer 360 collect, the classic Add-payment form, invoice "Pay", staff cash), which is
  why nothing could save. It was NOT the migration and NOT the schema — the column exists; the code just
  couldn't reach the insert.

  Silver lining: the error fired INSIDE the transaction, so every failed attempt rolled back cleanly —
  no half-written OrderCost/CustomerPayment rows, no double posts. Your data is intact.

THE FIX (one line)
  app/Services/Money/PaymentService.php, line 51 — add $idem to the closure's use(...) list:
      DB::transaction(function () use ($t, $d, $orderNo, $costNote, $customer, $idem) {

VERIFICATION DONE HERE
  php -l clean. Confirmed every variable the closure body references is now either captured
  ($t, $d, $orderNo, $costNote, $customer, $idem) or a local ($cost, $pay).
